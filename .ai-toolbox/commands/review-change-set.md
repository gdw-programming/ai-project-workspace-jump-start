# Review Change Set

**Aliases**: `review-change-set`
**Purpose**: Verify a change set is consistent, correct, and ready to record
**Pattern**: Review all version-controlled files in the current change set (exclude gitignored and intentionally untracked files) against established context rules. This command is stateless: at the start of every run, re-read the current git/workspace state directly instead of relying on earlier session memory, prior command output, or assumptions about what is staged or modified. Manual user edits, staging changes, branch state, or file updates made between agent turns must be reflected immediately. Check whether any unstaged-but-edited file is required by a staged file or by the staged change set as a whole; if so, stop and ask the user whether they intend to leave that file out of the commit and confirm that the final committed state still works without it. Synchronization edits are part of this command's duties: when repo state, file trees, directory references, or auto-sync targets are stale, correct them as part of the same review before finishing. When issues are found, apply judgment on scope: make small corrections directly (broken links, stale references, isolated wording fixes, single-file line-level changes, and sync drift fixes) then report what was changed for user review; for large issues (structural changes, multi-file impact, or anything requiring a design decision) report the issue and ask the user whether to proceed before acting. After all fixes are applied, re-read changed files to verify no fix introduced a new inconsistency. Report the final review outcome. The user may then stage the fixes and request another review pass to confirm the change set is clean. See the Workspace State Awareness rule in `context.global.md` for the root requirement and do not reinterpret or replace it here.
**Context**: context.global.md + ../STATUS.md + all version-controlled files in the current change set
**Checklist**:
- Stateless execution: re-read the current git/workspace state at command start every run; do not reuse results from an earlier turn or assume the workspace is unchanged since the last review
- Manual user actions between turns are included: file edits, staged/unstaged changes, and branch/state changes discovered since the previous run must be reflected in the current review
- Unstaged-file dependency check: identify any unstaged file that is edited but not staged and verify whether it is required by a staged file or by the staged change set; if it is required, ask the user whether the exclusion is intentional and whether the final commit still works without it
- Logical consistency, clarity, and alignment with project workflow goals; no rule or constraint conflicts with an existing rule in another context file
- Compliance with all context and documentation rules (DRY, Minimal Context, Workflow Agnostic, Reference Validation, Language Standards, Markdown Links, Context Framing)
- All file references and links are correct and point to existing files
- Workspace tree and any directory/file-tree references in STATUS.md, README files, and other structured summaries reflect all files in this change set — treat them as current and update stale listings before closing; this includes synchronization edits as part of the command's core duty
- BACKLOG.md and CHANGELOG.md are current (if the project uses built-in tracking files) — any project deliverable items completed in this change set are recorded with contributor name and date; context system maintenance is not recorded; age-out criteria in BACKLOG.md has been applied and stale entries removed
- Auto-sync targets are consistent with current content — root README.md always; STATUS.md, BACKLOG.md, CHANGELOG.md only if the project uses built-in tracking files — fix any out-of-sync targets immediately as a dependency, including synchronizing file-tree and status references as part of the same review
- Staged/unstaged cross-check: any reference in a staged file to another file (import, path, link) must resolve against staged content — an unstaged file referenced by committed code will break anyone pulling the branch
- Dependent context files updated: all context files (domains/, tools/, commands/, context.*.md) that reference deleted or renamed code, APIs, or file paths are updated in this change set
- Knowledge capture: identify any framework behavior, fragile patterns, or tool internals discovered during this work — verify they are captured in the appropriate context files per the Knowledge Capture rule before closing
- No non-productive content: remove any files or sections that serve no ongoing operational purpose - initialization summaries, one-time status dumps, redundant checklists, or content that duplicates what a live context file already provides authoritatively
